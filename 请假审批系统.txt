十一、请假审批流程

核心流程：

申请人提交请假申请
→ 直属领导审批
→ 部门经理审批
→ 审批完成。

支持根据配置启用、停用、调整审批节点和审批人员。

11.1 提交请假申请

接口建议：

POST /api/leave-requests

请求包含：

LeaveType

StartTime

EndTime

Reason

可选的附件信息，或者通过 multipart/form-data 上传多个附件。

提交后执行：

从当前登录用户上下文获取申请人 ID。

验证请假参数及附件。

根据申请人的部门或适用范围获取当前有效流程配置。

校验流程配置有效，存在有效节点及审批人。

创建请假单并生成唯一业务单号。

保存附件元数据和文件。

按当前流程配置生成实际审批任务及审批人快照。

激活第一个节点的待审批任务。

写入提交操作记录。

在数据库事务中保证单据、任务和记录的一致性。

提交成功后，通知第一个节点的待审批人。

返回单据编号、当前状态和必要的业务信息。

不要在数据库事务尚未提交时发送不可撤销的外部通知。

可以通过事务提交后的通知机制或简单的 Outbox 模式实现可靠通知。若采用简化实现，必须处理通知失败与数据库成功之间的不一致问题，并在 README 中说明当前可靠性边界。

11.2 审批同意

接口建议：

POST /api/leave-requests/{id}/approve

请求包含：

Comment：可选审批意见。

执行要求：

根据当前用户获取审批人 ID。

查询单据及当前待审批任务。

校验单据存在。

校验单据处于允许审批的状态。

校验当前用户是该单据当前节点的有效审批人。

校验任务仍为 Pending，防止重复审批。

在事务内完成当前任务、审批记录和单据状态变更。

若存在下一节点，激活下一节点的任务。

如果下一节点存在多个审批人，按照明确的节点规则分配任务；默认采用节点内任一指定审批人完成即可流转的简单策略，并确保其余任务同步失效。

若不存在下一节点，将单据状态更新为 Approved，并记录完成时间。

处理并发审批，确保同一任务不能被成功审批两次。

事务提交后清理相关缓存，并向下一审批人发送邮件；若流程结束则可通知申请人。

同意操作不得允许用户跳过节点，也不得接受客户端传入的下一审批人来决定流程。

11.3 审批驳回

接口建议：

POST /api/leave-requests/{id}/reject

请求包含：

Comment：必填驳回意见。

执行要求：

校验当前用户身份和审批权限。

校验单据当前状态和待审批任务状态。

在事务内将当前任务更新为 Rejected 或其他明确的终态。

将请假单状态更新为 Rejected。

写入完整审批记录及驳回意见。

使该单据其他尚未激活或尚未处理的任务失效。

事务提交后清理详情缓存及相关待办缓存。

通过邮件服务通知申请人驳回结果和驳回意见。

驳回后不得继续流转到后续节点。

缓存键需要包含用户 ID、页码、每页大小及所有会影响结果的过滤条件。

13.3 缓存失效策略

提交、审批通过、驳回、取消等影响流程的操作完成后，清理或失效：

对应请假单详情缓存。

当前审批人的待办缓存。

新激活审批人的待办缓存。

流程结束时申请人可见的相关查询缓存（若实现了该类缓存）。

缓存失效必须发生在数据库事务成功提交之后。

如果 Redis 失效失败，记录异常并提供合理的重试或版本号机制，避免长期返回明显过期的数据。

请在 README 中说明缓存一致性策略和已知边界。

十八、事务、一致性与并发控制

重点实现以下业务一致性：

请假单、审批任务、审批记录在关键操作中保持事务一致性。

两个并发请求同时审批同一任务时，只能有一个成功。

重复提交相同审批操作时，不能重复流转。

数据库提交失败时，不得提前通知审批人。

Redis 失效只能发生在数据库提交成功后。

文件写入、数据库写入和邮件通知之间不存在天然的分布式事务，必须采用合理的补偿、重试或 Outbox 策略。

如果实现 Outbox，至少包含消息类型、业务标识、序列化内容、创建时间、发送状态、尝试次数、下次重试时间及错误信息。

对并发异常、唯一键冲突、缓存异常和邮件发送异常进行适当处理。

不要声称 Redis、mysql、文件系统和邮件服务之间具备不存在的原子性。

对于审批操作，推荐采用数据库事务、任务状态条件更新及乐观并发控制的组合方案。必要时可使用 EF Core 并发令牌或条件更新确保单个任务只能被处理一次。
